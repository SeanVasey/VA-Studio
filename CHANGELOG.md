- FP-028, scheduler and backup signals on the admin dashboard. The fourth widget (now titled "Scheduler, backups and host") reads real data instead of always showing Unavailable. `vasey:scheduler-heartbeat`, scheduled every minute, upserts one row in the new `scheduler_heartbeats` table; "Scheduler last run" is OK up to `REPORTING_SCHEDULER_HEARTBEAT_STALE_SECONDS` (300), Needs attention after it, and Unavailable until a heartbeat is recorded. The three existing scheduled commands record their latest exit outcome (`OperationalSignals::track`, best effort), and "Scheduled commands whose latest run failed" names any that failed. `php artisan vasey:backup-record --kind=daily|restore-drill --status=ok|failed [--bytes=N] [--sha256=HEX]` appends to the new append-only `backup_evidence` table (triggers refuse UPDATE, DELETE and malformed rows on SQLite and MySQL; rollback refuses once a row exists); it takes no path or free text and never echoes a refused value. "Last successful backup" is Needs attention when the latest run failed or the success is older than `REPORTING_BACKUP_STALE_HOURS` (26), and "Last successful restore drill" after `REPORTING_RESTORE_DRILL_STALE_DAYS` (35); both are Unavailable until recorded. The nightly run of `ops/staging/backup.sh` (and the derived production kit) records its outcome after the resume, as the application user, failure-tolerant; restore drills are recorded by hand. Host health stays Unavailable by design: Forge and `ops/monitoring/host-baseline.sh` cover it. Thresholds are in `config/reporting.php` and the env examples; a threshold below 1 shows Unavailable. The installed backup helper must be reprovisioned before the next deploy (the helper drift check). Tests: `OperationalSignalsTest` (freshness boundaries, never-recorded, failed latest run, validation, append-only triggers, widget states, staff-only), the updated `OperationalHealthTest`, `tests/ops/test_staging_backup_evidence.py`. Docs: `docs/staff-reporting.md`, `docs/ops/monitoring-and-host-baseline.md`.

- FP-076 / U-13, first increment (non-destructive): a retention schedule and a read-only dry-run report. `App\Domain\Customers\DataRights\RetentionSchedule` classifies each table of every `CustomerDataRights::RETAINED` record family, and every table the data-rights export and deletion read, exactly once. Each table gets a class (`financial`, `consent`, `correspondence`, `security`, `indefinite` or `not_applicable`), the timestamp columns that start its clock, and a rationale. Order snapshots, licenses, contracts, verified payments, purchase claims, production checkout records, paid-grant origins and originals, and order-linked conversations are `indefinite`: never counted, never purged by this mechanism. Download records are `financial` with a minimum period only, because the license lifetime still applies. Consent and suppression ledgers are held: their clock (while the email is held, plus 3 years) is not modeled. `php artisan vasey:retention-report` counts, per class and table, the rows past the configured period, with the oldest and newest due dates. It uses plain selects in primary-key chunks of 10,000 and prints no identifiers or personal data. It refuses with a non-zero exit while any `customer-data-rights.retention` value is unset or invalid (periods are set per host, never in Git) or a scheduled table is missing. No delete or anonymize code path exists; a purge needs its own reviewed migration and Sean's authorization. Tests: `CustomerDataRetentionReportTest` covers classification completeness (source scan of the data-rights code, RETAINED families, no class loosening), refusals, synthetic records aged by time travel across classes, read-only queries and no personal data in the output. Open questions for Sean are in `docs/customer-data-rights.md`.
