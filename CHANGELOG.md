- Staging ops, shorter deploy downtime: the backup set's private store is a tree that shares unchanged files with the set re-hashed before the quiesce (2026-11-11; on staging each deploy was down about 22 minutes, 21 of them tarring the ~38 GB private store and extracting and re-hashing it in the restore proof). New `ops/staging/private-snapshot.py` (installed as `/usr/local/libexec/vasey-staging/private-snapshot.py`, copied byte for byte into the production kit): the snapshot copies every private file that is new or changed (identity = device, inode, size, mtime and ctime in nanoseconds against what the source set recorded; a change within 2 s of that snapshot's start, or during the copy, is never trusted) to a new root-owned inode, and hard-links unchanged files only to the copies of the one set this operation re-hashed in full before its quiesce (`space-check --preverify`, run by `ctl prepare`, `ctl refresh` and the nightly run; it writes a single-use token `backups/.link-token` outside every set, refused after 6 hours), only while each such inode still has the identity, ctime included, recorded by that re-hash, never to the live store and only on one filesystem; anything else is copied (EXDEV and other link refusals included). Every directory and file is opened relative to its parent descriptor without following links (and files non-blocking), so a symlink or FIFO swapped in during the walk is refused. A failed re-hash withdraws the `RESTORE_CHECK` of that set and of every tree set sharing a failed inode, and makes the deploy refuse before its quiesce (the nightly run copies everything instead); `ship-pending` skips a withdrawn set with its own reason and ships the others. The in-window proof verifies the tree in place (names, directories, modes, root ownership, SHA-256 of every copied file, exact inode identity of every shared one) instead of extracting it; the database proof is unchanged and still gates every migration; `restore-check DIR` re-hashes every file and also proves a set moved to another disk or extracted from an off-host archive (new inodes, whole-second mtimes); sets with `private.tar` are still proven, shipped and pruned as before. `space-check` counts only the bytes the snapshot will copy and the database twice (plus the whole set for an encrypted shipment). Optional `backup.conf` key `VASEY_BACKUP_LINK` (1; 0 copies the whole store every time). Directory mtimes are not kept in a tree set. Runbook section 8 ("The private store is a shared tree", "What changed for an operator") and case B (restore from a tree set), README, off-host hardening restore drill. Expected quiesce on staging: about 2 to 4 minutes instead of 22 (estimate, not measured on the host); the first snapshot after re-provisioning copies everything (about 5 to 9 minutes in the window). Before the application trusts a `clamdscan` answer it now asks the daemon to scan a sparse file of 4 GiB and a byte (no data, and no disk where the filesystem keeps holes in a file; made in the scan's own workspace and removed afterwards) and requires `Heuristics.Limits.Exceeded.MaxFileSize FOUND`, which ClamAV 1.5.4 gives at every limit when `AlertExceedsMax yes` is set and never gives without it. Otherwise the scan fails as `scanner_unavailable`, before the upload reaches the daemon, and the worker log names the fix (`MaxFileSize` and `MaxScanSize` at the documented value, `AlertExceedsMax yes`). The daemon is asked on every scan, and nothing is remembered: the canary costs about what the version call before it does (a median of 7 ms against a real clamd), and a daemon reconfigured to fail open is caught by the next scan. `php artisan vasey:doctor` gains the same check as `media_scanner_limits`, with its canary made in a scratch directory of private storage, as a scan makes its own, and removed again (with `processing/`, if the doctor made it); it makes nothing where private storage does not exist, or for a user who does not own it, so run it as the worker's user (`sudo -u <worker user> php artisan vasey:doctor`): a run that a signal interrupts skips its cleanup, and the `processing/` that root left behind would stop a worker of another user from making its own workspace. Upgrade note: a worker that may not write a file of 4 GiB (`ulimit -f`, `LimitFSIZE=`), or whose PHP lacks the `posix` extension that reports that limit, can no longer use `clamdscan`; the scan fails as `scanner_unavailable` without making the file. Nor can one whose private storage does not keep holes in a file: a filesystem without them would write all 4 GiB for every scan, so the canary grows to 64 MiB first, and when more than 1 MiB of it is allocated the scan fails as `scanner_unavailable` before the daemon is asked, after at most 64 MiB written. ext4, ext2, tmpfs and ramfs allocated nothing at 64 MiB or at 4 GiB and a byte; no filesystem without holes was at hand, so that refusal is tested with a stand-in. The worker log says which of these it was, and names no `clamd` setting for a canary that could not be made.
- When a scan does not finish, the worker log records why: the failure, the exit status (137 is SIGKILL, which is how the CPU limit ends a scan) and the first line the scanner wrote to standard error and to standard output, without the upload's directory and at most 200 characters.
