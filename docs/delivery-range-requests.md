# FP-077 — HTTP range requests for private delivery: design and blockers

Status: **design only, 2026-11-09. No delivery behaviour changed.** Every customer download path still refuses `Range` and `If-Range`. A working prototype for the test-delivery chain is preserved on the pushed, unmerged branch `claude/download-range-requests-20261109-prototype` (draft PR, not for merge) (described under [Prototype](#prototype)). It was not merged because enabling it would contradict the approved test-delivery policy contract (blocker B1). The prototype also does not give buyers a resume they can use today (blockers B2 and B3).

## What exists today

Source read on `main` at `69a474a2`.

| Path | Route | Range handling | Redemption model |
| --- | --- | --- | --- |
| Test delivery (staging rehearsal) | `POST /orders/{order}/delivery/download` | `TestDeliveryPrivacy` answers 416 `INVALID_DELIVERY_REQUEST` for `Range`/`If-Range`; `TestDeliveryResponse::protect()` strips `ETag`, `Last-Modified`, `Accept-Ranges` | One `test_delivery_redemptions` row per authorization (unique), 60 s authorization lifetime, three new authorizations per order per rolling 60 s |
| Paid (V1) | `POST /paid-grants/authorizations/{authorization}/redeem` | `PaidGrantPrivacy` refuses both headers | One `paid_redemptions` row per authorization; `max_downloads` (1–100) counts redemptions per origin; `authorization_seconds` 30–600 |
| Paid-tax (V2) | `POST /paid-tax-grants/origins/{batch}/authorizations/{authorization}/redeem` | `PaidTaxPrivacy` refuses both headers | Same shape as paid (`paid_tax_redemptions`, `max_downloads`) |
| Free | `POST /free-grants/authorizations/{authorization}/redeem` | `FreeGrantPrivacy` refuses both headers | One `free_redemptions` row per authorization; `max_downloads`, `token_ttl_seconds` |
| Production free | `POST /production-free-grants/authorizations/{authorization}/redeem` | `ProductionFreePrivacy` refuses both headers | `already_redeemed` after one `production_free_redemptions` row |
| Member, listening library | none | Not applicable: no member file-download route is mounted; the listening library and its export are JSON | — |

Integrity is the same everywhere: each redemption copies the private object into an unlinked spool snapshot and reads the whole snapshot back against its retained SHA-256 before the first byte (`PrepareTestDeliveryStream`, `PaidGrantPrepareStream`). There is no cached verification keyed on file identity, and the D-19 guide rules one out: "Cached integrity success cannot replace fresh physical reads" ([test-owner-delivery.md](test-owner-delivery.md)).

## Blockers

**B1 — the approved test policy says ranges are disabled.** `TestAccessPolicy::CONTRACT` contains `"stream_attempts": 1` and `"ranges": "disabled"`. Operators configure that exact JSON (`VASEY_TEST_DELIVERY_ACCESS_POLICY`, `ops/staging/test-commerce/env.test-commerce.example`), and `scripts/ops/validate-test-commerce-profile.php` checks it. The contract is also frozen inside each authorization's encrypted evidence (`DeliveryAccessEvidence::capture`) and verified canonically on every read, and the schema trigger in `2026_09_26_000023_test_owner_delivery` admits only `policy_version = 'test-owner-delivery-v1'`. Serving ranges while that policy is in force would make the approved literal false. Doing it properly needs a `test-owner-delivery-v2` contract, a trigger migration on SQLite and MySQL (alongside the byte-exact guards of migrations 000029/000030), evidence verification by each authorization's own policy version (so v1 history still verifies), validator and environment-example updates, and amendments to D-19 ("permits at most one committed stream attempt") and D-20 ("disable range/conditional caching behavior"). Changing an operator-approved policy and two accepted decision records is Sean's decision, not an implementation detail.

**B2 — every download is a POST.** D-20 chose a CSRF-protected POST body for the secret and rejected token-bearing GET links and JavaScript blob downloads. RFC 9110 section 14.2 defines range handling only for GET and says a server must ignore `Range` on other methods unless something defines it. A custom definition for these POSTs is possible, but browsers' native download managers do not resume POST downloads. Only a scripted client (a CLI, a download manager that replays POST bodies, or an in-page fetch downloader, which D-20 excludes) could use it. Buyer-visible resume needs a transport decision: for example a GET to a single-purpose, short-lived, non-reusable capability URL with `Referrer-Policy: no-referrer`, which reopens D-20's leakage analysis.

**B3 — authorization lifetimes are shorter than the transfers that need resume.** Expiry bounds when a request may start: 60 s for test delivery, at most 600 s (plus a 60 s authorize budget) for paid. A transfer that drops after that cannot resume on the same authorization, and allowing it would extend use past expiry, which this design refuses. Resume therefore usually needs a fresh authorization, and in paid, paid-tax and free each redemption counts toward `max_downloads`. Whether a fresh authorization redeemed only for a partial range counts as a download is a licensing and support decision.

**B4 — four production-bound chains need their own work.** Paid, paid-tax, free and production free each have their own frame and commit machinery (`PaidGrantCommands`, closed projection reads, per-buyer spool slots, a transfer deadline counted from the redemption commit, append-only redemption triggers). A resume branch has to be built, raced on native MySQL and independently reviewed in each, after B1 to B3 are settled. The test chain is only the staging rehearsal path.

## Recommended design (when unblocked)

The prototype implements this for the test chain; the same rules should apply to every chain.

- **Selection** (`DeliveryByteRange`): a single `bytes` range, RFC 9110 grammar (`a-b`, `a-`, `-n`; unit case-insensitive; `b` clipped to the last byte). Anything the server may ignore is a full selection: no `Range`, an unknown unit, malformed syntax, `b < a`, any multi-range list, a header over 128 bytes, an `If-Range` that is not a strong match of this file's ETag (weak tags and dates never match), and a range covering every byte. `a ≥ size` and `-0` are unsatisfiable. `If-Range` is evaluated first, so a failed validator sends the whole file even for an unsatisfiable range. Multi-range is served as a full 200, never `multipart/byteranges`.
- **Authorization and counting:** the selection is evaluated only after the owner and token match, and the redeeming command re-checks it against its own read of the retained size and hash. A full selection needs an unredeemed authorization and records its one redemption, as today. A partial selection runs every existing check (owner, token, policy, account, control version, refund/dispute, evidence and redemption evidence, expiry) both before the snapshot and under the order → control → authorization locks. It records the redemption only if none exists; on an already redeemed, unexpired authorization it resumes that redemption, writes no redemption row and is audited as `commerce.delivery.resumed`. A full selection on a redeemed authorization stays 409 `DELIVERY_ATTEMPTED`, so a range cannot launder a second full download. One full request plus any number of ranges records exactly one redemption.
- **Unsatisfiable:** after the same checks (including under the locks), with no private file access and no consumption: 416 `DELIVERY_RANGE_NOT_SATISFIABLE` with `Content-Range: bytes */<size>`. An expired, withdrawn or foreign authorization gets the same refusal as a full request (410, 503, 404), never 416.
- **Expiry:** admission still requires `now < expires_at`, before the snapshot and at commit. A range never extends use past expiry; like a full stream, an admitted range may finish after it.
- **Integrity:** the whole snapshot is copied and its SHA-256 read back before any byte, for full and partial selections alike; the partial response seeks within that verified, unlinked snapshot. The cost is one full read and spool copy per resumed request, bounded by the existing three spool slots (3 GiB). A tampered file is refused (503) before any byte, including bytes outside the requested range.
- **Headers:** 206 with `Content-Range: bytes a-b/size` and the range's `Content-Length`; 200 and 206 both carry `Accept-Ranges: bytes` and a strong `ETag`. The ETag is a domain-separated digest of the content hash (`sha256("vasey-test-delivery-etag-v1:" + sha256)`), not the hash itself, because delivery responses do not expose retained evidence hashes. `Cache-Control: private, no-store`, `Vary: Cookie`, `nosniff`, `no-referrer` and `noindex` are unchanged; `Last-Modified` stays stripped. Error responses carry no `ETag` or `Accept-Ranges`. Other delivery routes keep refusing range headers with 416.

## Signed-link retry

No signed or reusable download link exists, and none is proposed. Retry is documented behaviour: a failed or interrupted attempt is recovered by requesting a new authorization (a new idempotency key), subject to the rolling budget and, in the paid chains, `max_downloads`. An authorization's secret is never recoverable and a committed attempt is never restored ([test-owner-delivery.md](test-owner-delivery.md), [test-owner-delivery-http.md](test-owner-delivery-http.md)). The FP-077 acceptance line "signed-link retry documented" is met by this statement; "range/resume where supported" remains open on B1 to B4.

## Prototype

Branch `claude/download-range-requests-20261109-prototype`, commit `bca8f6ca` (pushed for preservation; not for merge as is). It adds `App\Domain\Delivery\DeliveryByteRange`, `PreparedDeliveryStream::writeRangeTo()`, a range-aware `RedeemTestDelivery::handle(..., ?DeliveryByteRange $range)`, the controller, response and middleware wiring, `tests/Unit/DeliveryByteRangeTest.php` (37 cases) and `tests/Feature/TestOwnerDeliveryRangeTest.php` (17 cases: exact 206 bytes for closed, open, suffix and clipped ranges; resumes sharing one redemption; full, whole-file, malformed, multi-range and failed `If-Range` requests refused after redemption; ignored ranges served whole; 416 without file access; expiry, policy withdrawal and control block; another session and a wrong token; a tampered byte outside the range; GET and issuance still 416; a stems archive resumed through the domain command). Its commit message records the commands and results. It leaves the policy contract at v1, which is exactly why it is not mergeable (B1).
