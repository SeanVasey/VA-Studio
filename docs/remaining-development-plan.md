## Working method and ownership

The implementation lead owns sequencing, integration and evidence. Use up to three independent contributors when useful: domain/backend, UI/design, and tests/operations/source analysis. Each owns named files in a branch/worktree; only the lead integrates. Independent reviewers assess money, licensing, access, migration and CI-gate changes.

1. Select a dependency-ready outcome and define its behavior, API/state contract, owned files, focused tests, rollback and relevant policy decisions.
2. Implement related changes with their UI and adversarial regressions in small commits. Default batch size is two to four related deliverables, reduced when a migration or financial state machine warrants a separate review.
3. Run focused checks during implementation. Freeze the candidate before expensive final CI. Review and repair locally/in the focused cloud lane before opening a ready PR.
4. Run the full applicable suite once on the integrated final candidate. A substantive correction requires new evidence for the corrected source; earlier green results do not transfer automatically.
5. Merge only the verified source, then continue the next independent workstream. While a final suite runs, do source review, design, or development on a separate branch without modifying the candidate or claiming an untested combination is accepted.
6. Update task statuses and the ordered record in the same feature change. Put run-specific counts/links in the PR after tests finish; avoid a new documentation commit whose only purpose is to restate its own passing run.
7. Reconcile the branch/base before the next integration. Do not merge parallel branches solely because each passed against an older base.

This replaces repeated one-fix/one-full-run stops with complete feature batches. It does not create a giant end-of-project merge.
