# Recognizable original purchases and fresh library pages

This T24/WP-08 child builds on `76086817453d7a67c9f56dc31a34a601464857a6` (tree `fd14b9e1ecdaba300d59383f0697b22f065acef9`). It makes the existing test library and guest history usable without remembering every order reference: each card names its first original item and license version, reports the total item count and retained payment/contract status, and offers Older, Newer and Newest navigation. Full original items and downloads remain deliberate existing actions.

## Contract and boundaries

`GET /orders/history` retains its canonical optional `before` UUID and changes only its response to `orderHistorySchema: 2`. The existing `orders` summaries are unchanged. An equally sized, ordered `previews` list carries exactly `orderId`, `itemCount` (1–10), and `firstItem` with `title`, `licenseName`, and positive `licenseVersion`. The first-item label describes one line, not every item or license in that order. Names preserve their original UTF-8 text, bounded to 255 code points each.

`ReadOrder::historyEntry` reconstructs each authorized original once and derives its summary and preview from that same verified payload. It does not use today's catalog or license name, fetch per-card item endpoints, rewrite historical evidence, or grant rights. The history query still selects at most 21 candidate order rows and projects at most 20; existing account/original-owner/explicit-claim checks and final claimed-order availability checks remain in place. Original status, exact-reference lookup and original-items DTOs retain their previous contracts. No database migration, provider call or new financial/access transition is introduced.

The history reader has a dedicated **192 KiB streamed byte ceiling**: twenty pairs of maximum 255-code-point names can exceed 128 KiB when supplementary Unicode is escaped in JSON. The reader also verifies content type, status, redirect absence, exact DTO keys, unique order identities, matching preview positions, count/text/version bounds and cursor coherence. The existing download response ceiling is unchanged. No private response text is reflected on failure.

Newer navigation stores only a component-memory trail of previously used `before` cursors. Every page is freshly fetched; no old order payload is reused. Cursor changes commit only after a valid response. Refresh and Newest start again at the newest page. Navigation immediately clears visible rows and expanded details; a failure clears the trail, and access failure requires fresh sign-in. Page departure and unmount abort requests, dispose their deadlines and discard private state. Each request owns its controller/generation/deadline, so a delayed old completion or cleanup cannot replace or unlock a newer request. Each request has a 20-second deadline. No order history, titles, account details or cursors are written to browser storage or URLs beyond the existing current HTTP cursor.

This is bounded browsing, not global purchase-title search, production account/recovery acceptance, resumable large-file delivery or complete T24 acceptance. Existing local/testing gates, original download budgets and immutable owner/payment/grant/contract/asset evidence remain unchanged.
