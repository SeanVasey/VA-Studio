## Durable choice and delivery

Each accepted explicit withdrawal advances the existing consent revision and atomically appends an intent for the server's canonical current account recipient. An encrypted account/purpose/recipient target is reused across repeated withdrawals. Failure to save the target/intent or terminal authority/configuration proof rolls back the choice and the outbox append together. Historical consent rows receive no invented/backfilled suppression intent. Granting consent never removes suppression history or invokes unsuppress; changing the current recipient selects only its own target.

`SuppressionDelivery::process(CustomerPrincipal, User, int expectedConsentVersion)` and `::reconcile(...)` are private server entry points, with no HTTP route or automatic dispatcher. Both require the existing current account policy, matching actor/credential/access revision and exact current consent revision. They refuse a caller's outer transaction, because a delivery marker must commit independently before a transport can run. A reviewed production authority adapter remains a separate dependency; this child adds no permanent production environment rejection of its own and does not weaken the current account guard.

One immutable attempt is permitted per target. The first transaction commits its operation ID, captured access revision, encrypted exact server binding and canonical request hash. The second transaction rechecks fresh recipient, version, binding and current authority before any adapter invocation while retaining the account locks. A failure after the claim commit leaves a durable unknown outcome even if the transport probably did not run. Subsequent process calls never resend an existing attempt. Repeated withdrawals advance the choice and append intents without resetting that marker. Reconciliation calls only `inspect`; it never calls `suppress`.

Only an authenticated exact positive receipt translated by the reviewed scope-specific adapter may confirm the captured operation/recipient/binding/request hashes. Null, exception, malformed, mismatched and ambiguous outcomes stay unknown. An encrypted bounded receipt and canonical hash are retained only after exact matching and fresh terminal proof. A late credential, policy, recipient or row change prevents confirmation; the prior committed attempt remains available for inspection. A changed/disabled provider binding makes an old confirmation unknown for the current configuration, without automatically resending or migrating its scope.

The adapter's `boundTo()` is a local binding declaration, not a provider request. Its error is generic. `suppress()` may make one bounded authenticated provider suppression request; `inspect()` may perform read-only reconciliation and must never resend. The default `UnboundSuppressionAdapter` has no provider credentials or implementation and is never invoked for transport. An HTTP 2xx or successful purchase/listening operation is not a positive suppression receipt or consent evidence. Every actual provider adapter and delivery policy still needs source-backed independent review.

Enabling requires literal boolean true and an exact binding with `adapter`, `version`, `scope`, `reviewReference`; arbitrary extra keys, absent/empty review, numeric/string truthiness and an unmatched adapter hash do not authorize a transport. Adapter/version are bounded ASCII identifiers (80 bytes). Scope/review reference each have at most200 Unicode characters/800 UTF-8 bytes with no control/format characters or surrounding whitespace. All reads are bounded to the current account/purpose/recipient or known referenced IDs, at most two rows per proof query. Framework/container/adapter callbacks occur before pure final configuration checks and captured-primary raw PDO row closure. No catalog, account or recipient history scan is used. Export/delete of listening feature data does not delete retained consent/suppression evidence.
