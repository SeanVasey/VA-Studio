# B4 production account-feature HTTP composition draft

This is preparatory design for the next dependency-ready batch after the actual controlled financial retrieval merge. It does not activate any customer route, identity binding, note promotion, marketing grant, email provider or host operation.

Compose the already reviewed 253 listening and consent domains through sealed `ProductionAccountFeatureAccess::forRequest` with server-fixed `listening_library` / `consent_preferences`. Retain the current production session marker, feature policy/provenance and historical binding rules. Do not borrow ordinary test principals, infer owners from email, adopt legacy listening/consent rows or duplicate business rules in React.

Ship a literal default-false HTTP mount under the closed account-feature parent. Own new production controller/request/privacy/mount classes, route file, page/component and focused tests. Coordinate changes to `routes/web.php`, `bootstrap/app.php`, `IdentityPrivacy`, account parent config and the CI selection manifests. Existing domain/schema/original policy/profile bodies remain dependencies; if a concrete related identity metadata correction is required, group it with its genuine regression controls and independent review rather than widening assertions about all shared V1 consumers.

HTTP operations are listening read / closed-empty initialization / versioned change / exact-version export, and consent read / closed-empty initialization / versioned change. GET never creates data. Initialization accepts only a duplicate-free empty JSON object. Listening change uses the reviewed 16 KiB bound; initialization, export-version and preferences use 4 KiB. Parse bounded raw duplicate-free JSON before invoking sealed services; domain command validation remains authoritative. Exact paths and response shapes must be checked against the existing root registration before implementation.

The existing global identity middleware currently admits every customer POST through its 4 KiB cap. Compose new feature privacy before it, while preserving existing identity request limits and errors. Require ordinary web session/CSRF, fixed HTTP methods, no query/method override/range/encoded body, same-origin requests and private no-store/noindex/no-referrer responses, including framework CSRF/validation/error exits. Error messages disclose no internal origin/account/recipient/principal IDs. An uncertain postcommit result requires read-before-new-versioned-intent; never automatically resend a mutation.

The new page presents explicit initialization, listening favorites/playlists/notes and own-data export, plus actual consent status and explicit withdrawal. It may present an affirmative grant only for the exact existing owner-reviewed purpose/notice hash; shipped purpose configuration leaves grants unavailable. Preserve unknown consent and unavailable-track placeholders. Bound client response reads to the reviewed 3 MiB listening/export limit and reject malformed output. Abort pending work on page exit; reconcile unknown outcomes through a fresh read.

Acceptance checks must exercise genuine production identity sessions and original 253 operations, default-off route registration, foreign-owner/test-session refusal, absent/invalid/replayed CSRF, duplicate/escaped keys, exact body boundaries and unknown postcommit readback. Verify closed-empty initialization, stale versions, missing storage read, own minimized export, explicit withdrawal with grant disabled and page lifecycle/error states. SQLite HTTP/frontend checks prove their recorded local scope; select meaningful private MySQL cases separately without claiming concurrency or host acceptance. Preserve unchanged frozen resources and all exact source/count/skip/runtime provenance. Independent review and cheap exact-head preflight precede an expected-SHA development merge.
