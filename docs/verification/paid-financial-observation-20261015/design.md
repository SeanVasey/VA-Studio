## Bounded provider normalization

`FinancialObservation::capture(FinancialExpectation, array $raw)` produces only a normalized internal observation value. Input follows the already retained own-account GET envelope: `account_id`, PaymentIntent, charge_before, bounded refunds/disputes lists, charge_after. Reject object-valued leaves/callback/coercion, invalid shape/depth/node/byte bounds before canonicalization. Bound total input1MiB, depth12,4096 nodes, at most100 members per list. Do not retain unknown sensitive provider fields or client_secret. All policy/config/source/byte limits refuse before invoking object code.

Bind own account, funds mode, PaymentIntent, latest Charge, original currency and exact integer gross/captured amount to the typed expectation. Require succeeded paid/captured collection; reject live/connected-account/application/transfer ambiguity and incomplete/partial collection. Stable normalized before/after Charge equality is a consistency check across separate GETs, **not** an atomic provider snapshot or settled balance. Preserve that distinction in the return type and docs.

Require actual list object, boolean has_more and dense bounded data. `has_more=true` returns/refuses as `incomplete`, never clear or empty. Validate each refund/dispute's exact parent payment/charge/currency/mode, unique bounded ID, integer amount and pinned supported status; sort canonical normalized items by ID. Refund succeeded sum is bounded by original gross; preserve pending/failed/canceled/requires_action statuses separately. Require consistent refund aggregate without treating pending/unknown states as settled. Dispute history and current Charge disputed bit remain separate observations; never infer automatic rights/availability effects from a status. Mismatch/unsupported/contradictory observations are attention/unavailable, never an asserted successful refund.

The internal value exposes only explicitly bounded factual summary/status/amount counts when requested; no raw provider/customer/credential payload, authority-bearing serialization or entitlement capability. Unknown/incomplete remains unknown/incomplete. Identical inputs canonicalize identically and cannot create monetary/business effects. The later durable ledger must own append-only sequence/idempotency/retention/authority; this slice does not invent those guarantees.
