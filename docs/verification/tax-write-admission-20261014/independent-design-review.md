## Required transactional-engine guard

There is no upstream runtime proof for Tax family InnoDB. Records/PrimaryBoundary do not include Tax tables, and they do not prove engines; the command frame's PDO transaction flag says nothing about an individual table's engine. TaxCheckoutSchemaInstaller checks ENGINE=InnoDB during install verification, but TaxCheckoutRecords::writer only reuses its weaker permanent-table prefix check. A permanent MyISAM table can pass that check, and an insert is already irreversible before a later admission rejects.

Adding TaxCheckoutRecords.php to this bounded scope is justified. Before any NEW Tax DML, open/pin each qualified physical family table under the original transaction, reject temporary identity, then use authoritative structured TABLE_TYPE/ENGINE metadata to require permanent InnoDB. Avoid a loose ENGINE substring in SHOW CREATE text/comments. Keep metadata identity pinned through DML/commit so another session cannot exchange the checked table; verify the chosen opening statement actually retains the required metadata lock, without adding unrelated global row contention. Preserve frozen V1. Native damaged-restore/nontransactional coverage must demonstrate refusal before INSERT/row growth, preserved prior evidence and proper frame cleanup. A post-insert engine check alone is inadequate.

Be precise about scope: same-session implicit DDL/direct PDO commit can destroy the original anchor and durably apply prior effects. A later refusal cannot undo them. Existing lost-anchor handling must not roll back a replacement frame or claim no row ever committed. Pre-DML damaged-engine refusal and postcommit/ownership-loss suppression are distinct observations.

## Meaningful focused regressions and existing flag oracles

The four tests observe a staged target through a genuine normal TransactionCommitting callback, then inspect physical row counts/family digests, callback leakage, native/framework idle, original dispatcher and positive retry. They are valid configuration-stop regressions. Binding/reviewed on old source can physically commit and only then fail status503; counting the target catches this whereas asserting an exception alone would falsely pass. They do not independently establish raw family/current-source/historical semantics.

Required complementary cases are:

- Representative current identity/catalog/candidate and genuine temporal withdrawal for order/request; exact family/selector and alias/shadow/original-frame refusal; no leaked afterCommit callback and clean retry.
- Positive binding/reviewed retention after current credential/account/access-version or current catalog/candidate withdrawal during provider I/O. The call may refuse subsequent status; independently assert the durable authenticated fact instead of demanding a stale-principal success response.
- Late confirmed payment retained as paid_exception with exact original observedAt/amounts; on-time observation remains classified on_time when persistence is later. Original identity history damage refuses, but harmless appended recovery history remains valid if historical plans are used.
- Native pre-DML nontransactional damaged-restore refusal; meaningful pinned-table/metadata identity proof for the chosen guard.
- Relevant parent/target/selector mutation during ordinary committing and multi-frame prefix preservation on later refusal. Retry uses original idempotency/session/payment identities and produces no ordinary grant/origin.
- Honest distinction between precommit rollback and aftercommit access/status refusal; no deletion, compensation or false successful fulfillment receipt.

Use completed old-source behavioral failures, focused affected SQLite and owned native driver selections, changed-file Pint and a final frozen independent source/evidence review. No routine full matrix or implementation-mirroring structural tests are requested. The design phase does not assign original reported1/3 or active executions a final result without actual closed receipt reconciliation.

## Explicit remaining pre-create boundary

NEW-write admission does not guard every future create. Existing-request prepare(create) is a READ frame without an observer, and postcommit/access callbacks also occur between a NEW request's physical proof and provider create. V1's reprove/proveCreatable exists for that separate final boundary. The corrected design explicitly leaves it subsequent; do not claim all stale/current-source provider I/O is now prevented. A later narrow pre-create proof must be independently specified/reviewed, rather than adding current catalog admission to binding/reviewed after I/O.
