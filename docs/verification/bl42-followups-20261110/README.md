## Refused-order resolution (Sean, 2026-11-10; branch `claude/refused-order-resolution-20261110`)

Sean: "restore the instrumental for sale and resolve it" for an unfinalized production tax order refused at finalization (fully refunded, or dispute lost). Built as `ResolveRefusedProductionOrder` plus the Filament list "Unfinalized paid production orders" (`ProductionTaxRefusedOrderResource`); see `docs/refund-dispute-lifecycle.md`, "Resolve refused order". Summary: same staff authority and MFA as `RefundDisputeActions`; provider IO through the finalize guard's `reviewedFacts` and `assess` outside transactions, re-checked under lock; proceeds only for a fully succeeded refund or a lost dispute; refuses finalized, clear, partial, open-dispute, in-flight, failed-read and unpaid orders; one append-only resolution row (migration `2026_11_11_000300`) plus an audit event; idempotent; creates no grant, license, contract or download authorization; `PaidTaxGrants::finalize` refuses a resolved order. Restoring the instrumental needs no release because this chain reserves no inventory and has no exclusive line (DD-14, C4); a test pins that every catalog table is unchanged and the offer can be ordered again. This closes the "lost dispute on an unfinalized order" gap noted for C1.

Open for review: the resolution is final, so it requires fully **succeeded** refunds (a pending refund is `in_flight`); a lost dispute with an open sibling dispute is `reconciling`. The database guards fix the row's shape and append-only behavior but cannot read the Tax255 or PaidTax tables (their installers refuse external objects that name them), so "paid, matching facts, no batch" is proven by the service under lock and the finalize frame, not by a trigger. The resolve-versus-finalize race relies on both taking the checkout order row lock and on locking reads of the batch and resolution tables; SQLite serializes writers, so it is covered by the lock order and the in-read finalization test, not by a native MySQL race test.
