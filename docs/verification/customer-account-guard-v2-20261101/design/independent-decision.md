P0 requirements:

- One closed account-parent classifier shared by IdentityMigrationOwnership and ConsentMigrationAdmission. It must select a whole exact stable V1 or V2 set, never per-trigger alternatives. Ordinary runtime rejects overlap and partial state. Preserve original 000040 bytes, v1 emitted definitions, historical fixtures and all user/quote/dependency checks. Inventory dynamic migration consumers: class availability and migration ledger are never version selectors.
- Transition ownership is migration-only and enumerated: exact old then exact v2 INSERT order, with exact unchanged UPDATE/DELETE; validate names, permanent table, namespace, timing, operation, body, creation SQL mode/charset/collation relevant to evaluation, and action order. V2 stable alone must have order1. Reject a v2 body under the old name, copied bodies on another table, extra BEFORE or AFTER triggers, case aliases, foreign views/routines/FKs, missing or altered/invisible/wrong-order unique indexes and temporary shadows. Do not weaken existing independent dependency ownership checks to obtain admission.
- Up/down must reinspect before every DDL, hold and finally release a same-connection database-scoped advisory lock, explicitly reject a preexisting transaction, and retain bounded metadata-lock failure. No catch-and-continue or IF EXISTS cleanup. CREATE overlap before DROP is necessary; never remove the last full guard. Runtime outage during exact overlap is intentional fail-closed behavior.
- Explicit migration ledger semantics: crash after CREATE but before ledger insertion resumes exact overlap; crash after DROP before ledger insertion resumes exact V2; repeated up at V2 verifies and does no DDL. A failed down retains its ledger row until complete, and a crash after restoring V1 before ledger removal must let down verify/no-op. Lost advisory connection must stop further work. Process termination releases lock but grants no authority to repair unknown objects. Do not manually mark a partial state migrated.
- Code deployment order is part of the contract: compatible admission code first, then migration; rollback restores V1 with new down before old application code. Fresh old 000040 creates V1, dynamically loaded identity/consent inspectors accept that V1 before late forward migration; V2 existing installs remain valid. Populated down changes only trigger version and preserves every row. Historical destructive rollback still refuses retained identities.
- Pin the selected exact version and namespace at each existing schema proof boundary. Inspect/frame caches cannot use stale V1 authorization after DDL or admit overlap on a memo hit. Keep existing metadata-lock/dependent proofs. The new helper must not grant general schema adoption/repair authority to unrelated consumers.
