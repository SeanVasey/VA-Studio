# Independent explicit file-provider refusal contract assessment

Reviewed root's proposed explicitly mutating fail-closed contract against exact PHP8.4.27 main/streams/userspace.c and streams.c, prior preconstruction assessment and own-kernel endpoint direction. Design/security source assessment only; no DB/network/container/CLI experiments/tests, implementation edits or agents. Root authorizes author source preparation/isolated pure CLI tests separately; this reviewer executes none.

Decision: DEFENSIBLE NARROW CONTRACT FOR SOURCE IMPLEMENTATION/ISOLATED TEST PREPARATION. Under its explicit trusted-baseline/single-thread assumptions, no unavoidable new P0/P1 is identified in the native restore-and-refuse mechanism itself. This resolves the earlier lack of a readonly pointer gate by changing the supported contract honestly: healthy provider has no mutation; altered provider may be restored and is ALWAYS refused/tainted before proc reads/new PDO. It does not yet approve an implementation, kernel tuple association or constructor security. Entire coherent exact source and actual native endpoint/budget evidence remain mandatory.

Exact native semantics support the distinction:

- userspace.c530-561 first retrieves the original global wrapper pointer. If current registry is global or current file pointer equals that original pointer,547-549 emits E_NOTICE “file:// was never changed, nothing to restore” and returns TRUE without registry mutation.
- If changed/unregistered,552-558 deletes the volatile entry and registers the original pointer, then returns TRUE without the no-op notice. A boolean TRUE alone is therefore never acceptance. Silent restoration must refuse, even though file is now native.
- streams.c2022-2026 clones the volatile registry with a NULL destructor; volatile unregister/register at2030-2049 perform hash pointer deletion/addition. In this exact restore path there is no call to user stream_open/read/stat/metadata/close methods. It is not opening the hostile wrapper. This matters: restoration can precede refusal without executing that wrapper's successful-read callback.
- Trusted native global wrapper table is an explicit prerequisite. This attests equality to PHP's process baseline, not arbitrary cryptographic proof that a native extension did not replace the baseline at startup. Trusted loaded code/extensions and fixed PHP8.4.27 are therefore part of this narrow profile.

Necessary implementation conditions:

1. Only the fully qualified exact internal builtin may be called with fixed literal file. Check critical globals are internal before using them; disabled/redeclared globals and namespaced shims cannot supply an attestation. No provider name/path/callback/options from configuration or caller. All relevant trusted helper/error classes must be loaded without letting this gate trigger an untrusted autoloader.
2. Install one fixed trusted temporary handler covering all relevant errors before the call. Record exact native E_NOTICE/error text as actually presented to PHP8.4.27 handlers (including any native function prefix), exactly once; require return TRUE and no other error/notice/exception. A substring match, E_USER_NOTICE, no notice, duplicate or unknown notice cannot pass. Do not invoke or chain the previous handler. Handler execution itself is trusted instrumentation, not authorization from caller data.
3. Restore the original error handler exactly in finally on every return/throw; preserve it as an opaque reference without invoking it. A failed install/restore/unknown state is refusal. Suppress/replace public error/exception chains with nonsecret reason only. No swallowed error may turn absence of a valid notice into healthy success. Unexpected fatal termination is not a normal successful restoration/constructor result.
4. Keep monotonic private lifetime poison. An altered-provider silent restore, unregister/missing baseline, FALSE, unknown error, handler failure, incomplete attestation or other unsafe result sets poison before any proc I/O/new PDO and never clears it. No reset API, object-local reinitialization, clone/serialize/destructor/finally clearing, or “now native so retry” acceptance. Check poison at subsequent relevant capability open/use boundaries, including reuse of already-created companion capability after another attempted admission taints the lifetime. Ordinary successful attestations must not write poison=false.
5. Do NOT restore the hostile wrapper afterward. The unsupported case's explicit request-local global side effect is restored native file provider plus refusal/poison; callers must not interpret it as supported repaired execution. No attempt to reconstruct/re-register unknown user wrapper class is safe. Other protocol wrappers remain untouched. Healthy no-op case should demonstrate registry/behavior equivalence.
6. Fixed trusted error-handler scope should cover the subsequent native proc enumeration/read/recheck as well, so open_basedir/permission/FD races cannot invoke ambient arbitrary handlers. It must not treat unexpected proc errors as provider-health success; they refuse/poison according to selected profile. Fully qualified function names and input/byte/fd/line bounds remain necessary.
7. Explicit supported execution model: one PHP thread/request execution, no fibers/coroutines yielding inside this section, no asynchronous user signal handler/extension hook changing registry/error-handler/config between gate and fixed reads/new PDO, no arbitrary PHP/RCE changing private poison or trusted code. Native proc data/kernel/net namespace must be trusted. A process/worker carrying poison cannot silently reset for the next identity operation; its operational recovery boundary must be explicit (e.g. restart). PHP-FPM request-local wrapper reset and long-running CLI worker lifetime differ; tests/documentation must say which lifetime poison covers.

Concrete counterexamples still rejected by this contract:

- Changed file wrapper returning plausible proc bytes: restore does not open it, no-op notice absent, poison/refusal before reads/constructor.
- Unregistered file wrapper: native restore may register original, but no no-op notice; still refusal, no repair-and-retry.
- Hostile preexisting error handler spoofing notice: replaced before native call and never invoked; only exact trusted native event counts.
- Disabled/redeclared or namespaced fake restore/file functions: internal-global admission fails before invocation.
- Existing companion reopened/reused after changed-wrapper refusal: global lifetime poison must forbid acceptance, not only count new constructors.
- Async/native baseline mutation or arbitrary reflection resetting private poison: outside the admitted execution model, not falsely claimed detected by pointer/no-op logic.

Preparation tests should run in isolated disposable CLI processes because poisoned cases intentionally alter request-local registry/error-handler state. Require wrapper method counters0, ambient handler counters0, proc-read counters0 and newPDOattempt0 on poisoned/missing/noninternal/wrong-notice paths; exact original handler restored; second healthy-looking attempt in SAME poisoned lifetime refuses; fresh healthy process succeeds without registry change. Include unknown notice/TRUE/FALSE, native E_NOTICE format, error-handler failure and exception cleanup pure cases. No DB/network is needed to establish those gates. Native direct-TCP/PDO-to-proc association and coherent both-array wrong-target no-handshake tests remain later separately scheduled proof.

This source-implementation direction is a meaningful scope adjustment already explicitly authorized by root/user's reversible engineering authority, not an implicit readonly claim. Final acceptance still depends on concrete code obeying all above and the previously required unique own inode/IP+source-port-before-target association, preconstructor double reproof, TLS/config preservation, historical bytes, primary authority/witness/MDL/temp/deadline and aggregate110/15 costs. No source freeze/native/production/member approval follows from this memo. Original failures retained, mount false and no accepted headroom.

Additional required source condition — stream context neutrality: create a fresh native empty context with explicit empty options/parameters and no notification callback, and pass it explicitly to every wrapper-backed proc read/directory operation supporting a context (including file_get_contents/scandir as applicable). Native file pointer attestation does not itself authorize ambient default-context callbacks. Never consume a caller/default context. For functions lacking a context parameter, either establish from exact native source that they do not consult/notify the ambient default or avoid them; fully qualified internal globals and fixed trusted error handler still apply. Context creation itself must use the admitted internal builtin, with no configuration object/callback or untrusted provider invoked. Include an isolated negative default-notification counter test so healthy native provider plus hostile ambient default context cannot execute caller code.
