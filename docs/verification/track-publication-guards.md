## Operator contract

In **Admin → Tracks**, opening **Publish** or **Unpublish** captures a confirmation for that exact current track and intent. Applying it rechecks current persisted staff authority/MFA, metadata revision, publication revision and state before any write. A changed metadata revision or intervening publish/unpublish cycle rejects the confirmation even if the current status and timestamps look the same. The failure remains **Publication blocked**; close and reopen the confirmation against current values. Cancel, another action or changed table context consumes the old confirmation. Submit consumes it before validation, authorization or a possible uncertain result and never falls back to immediate publication.

The confirmation does not establish readiness. Publishing checks the ordinary current rights, media and active-offer requirements inside its own transaction. Unpublishing removes public visibility while preserving the published URL, retained media, commercial/purchased evidence and publication timestamp. Each supported command advances only the publication counter and ordinary publication fields, plus its minimized actor/track/revision audit. Metadata revision is unchanged by publication.

## Strict command and authority boundary

`PublishTrack::review(Track, User, intent)` returns exactly schema version, actor ID, track ID, intent, metadata version, publication version and status. `publishReviewed` and `unpublishReviewed` accept only this canonical shape and their matching intent. Review and apply reject ambient transactions before private reads; ordinary readiness must not inherit a caller's earlier MySQL Repeatable Read snapshot.

Both lock the current persisted actor first, authorize the catalog Gate with its locking read and check current MFA, then lock the track. Apply verifies both revisions and status, checks signed counter capacity and current readiness, changes publication and records its audit in one transaction. Validation, authority withdrawal, stale/missing targets, exhausted counter, readiness failures and audit failure leave no publication write/audit by that attempt. Concurrent reviewed commands can commit only one revision from the same confirmation. Lock order remains actor → track without taking source/media locks after the track.

The existing two-argument `handle` and `unpublish` remain immediate trusted server compatibility commands: the supplied Track is identity, not an expected revision, and every call now uses fresh locking authority/MFA plus atomic counter/audit writes. They deliberately retain caller transaction nesting. A legacy caller-owned old MySQL Repeatable Read snapshot can therefore affect ordinary readiness child reads even after current actor/track locks. This is a compatibility limitation, not strict snapshot acceptance. All interactive callers and future scheduling integrations must use the standalone reviewed APIs; scheduling additionally needs pinned readiness evidence and its own due-time/supersession contract.

Filament disables action transaction wrapping for reviewed publish/unpublish. A server-locked confirmation and table context are captured only in the mount callback; submit cannot refresh a stale confirmation implicitly. Exact action/record/actor/intent identity and current context are checked before calling the strict domain boundary. Client changes to locked state are rejected, and cancellation/replacement/selection/table transport clears the review. Existing scoped private response and generic unexpected-error handling remain active.

## Additive schema and rollback

Migration `2026_10_02_000034_track_publication_version.php` adds signed integer `publication_version` with default zero. Existing rows, publication dates, URL reservations and audits remain unchanged; zero is a new counter baseline rather than invented historical revision evidence. MySQL/SQLite insert guards require the stored counter within 0–2,147,483,647; update guards also prevent decrease. Supported commands cannot write another revision at signed capacity. Arbitrary privileged SQL changing status without advancing the counter is outside this application publication contract; the migration does not impose a separate status-to-counter SQL trigger.

Before any repair DDL, migration preflight checks permanent table/engine identity, temporary shadowing, exact owned column/default/constraints, owned trigger definitions, installation order and retained values. Retry accepts only the migration's creation prefix: column, then insert guard, then update guard. Missing compatible suffixes are restored; incompatible definitions, impossible update-only installation, unowned counter constraints/indexes or invalid retained values fail before repair. No existing table row or audit is rewritten by recovery.

Apply the additive migration before exposing reviewed actions, with catalog writers paused during guard installation and existing MySQL trigger privilege available. `down()` intentionally retains the column, counter values, guards and audit history. For interface rollback, disable reviewed actions until compatible application code is restored; do not reset counters, remove guards/audits or resume an older writer that omits revision advancement. No production migration/deployment or restore rehearsal is claimed.
