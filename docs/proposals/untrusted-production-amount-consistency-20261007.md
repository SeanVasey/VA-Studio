## Supplied schema and report boundary

Proposed closed input v1 purpose: `untrusted_production_amount_comparison_input`. Required top-level keys are `schema_version`, `purpose`, `packet_public_id`, `retained_body_hash`, `requirements_hash`, `context`, `currency`, `minor_unit_exponent`, `tax_requirements`, `advertised_subtotal_minor`, `supplied_net_subtotal_minor`, `supplied_tax_minor`, `supplied_gross_total_minor`, `lines`. Context and tax-requirement objects must have the exact supported D-28 keys and exact retained values; no guessed defaults or absent tax behavior are filled in. Packet ID and both commitments must match the server-selected authenticated packet/requirements. Requirements hash is `CanonicalJson::hash` of the complete D-28 output.

Each supplied line has exact keys `position`, `track_id`, `offer_id`, `offer_revision_id`, `license_version_id`, `offer_snapshot_hash`, `quantity`, `advertised_price_minor`, `supplied_net_minor`, `supplied_tax_minor`, `supplied_gross_minor`. Require the exact frozen line order/identities/snapshot hash, quantity integer one, one to ten distinct lines and server-advertised price equality. All identifiers and amounts are exact bounded integers; reject floats, exponent strings, booleans, negatives, overflow, non-list lines, duplicates, omissions and extras. Bound canonical input size (proposed 16 KiB). Reject buyer/email/address/location, free-text references, provider object IDs/status, receipt provenance and any verification/assent/paid/execution flag; these fields have no authority in this input contract.

The report returns fixed version/purpose/canonicalization, packet ID, retained-body hash, requirements hash, canonical **normalized supplied-input hash**, `consistency_state` (`internally_consistent` or `inconsistent`) and a fixed non-PII reason code. Malformed input fails closed with a fixed validation message before hashing/echoing arbitrary data. Well-shaped mismatches return bounded codes such as identity, line, tax-constraint or aggregate mismatch; never echo raw supplied input or create an audit/persistent observation. Report hashes are internal semantic commitments, not substitutes for underlying encrypted-row proof or provider provenance.

Every report, including internally consistent input, keeps authoritative `amount_minor`, `tax_minor`, `total_minor` and `amount_observation_id` null and `amount_evidence_state: unobserved`. Require `payable`, `execution_allowed`, `external_facts_verified`, `provider_authenticated`, `payment_verified`, `buyer_identity_verified`, `buyer_act_verified`, `purchase_bound`, `rights_granted` and `consent_verified` false; `requires_current_eligibility_proof` true. Do not return an approved/payable verdict, authoritative tax/total or receipt-shaped object. Staff can supply a mathematically coherent fiction: the comparator must demonstrate this boundary in a positive test, rather than laundering that fiction into observed facts.

## Exact arithmetic scope

No currency conversion, promotion/discount allocation, bundle split, negotiated price, tax classification, quantity inference or repricing is introduced. Frozen one-unit prices and the retained software tax behavior are the only advertised operands.

For every candidate line require `supplied_gross_minor = supplied_net_minor + supplied_tax_minor` using bounded integer addition. Aggregate supplied net/tax/gross values must equal exact bounded sums of their corresponding candidate lines. Advertised subtotal must equal the frozen server subtotal, with line advertised prices matching every original price.

- **Exclusive behavior:** candidate net must equal the frozen advertised line price; gross must equal explicitly supplied net plus supplied tax.
- **Inclusive behavior:** candidate gross must equal the frozen advertised line price. Both net and tax must be explicitly supplied and satisfy the exact sum; never derive an actual tax/net basis from a rate or assume that a gross price is tax-free.
- **Provider-calculated strategy:** explicitly supplied candidate tax must be nonnegative and no larger than the software maximum-rate upper bound on explicitly supplied net. Reuse overflow-safe integer decomposition (or `MinorUnits::fraction(...)[ceiling_minor]`) solely as a comparison upper bound. This is not a jurisdiction/rate decision, expected tax, actual provider calculation, rounding attestation or an implementation of provider-exact rounding. Zero candidate tax can be internally consistent and still completely unverified.
- **Declared-exemption strategy:** a supplied zero tax candidate can be numerically compatible with retained zero-rate/not-applicable software requirements. Missing tax must not be filled with zero, and a compatible candidate must not prove an exemption or produce an authoritative zero-tax total. Qualified exemption evidence remains outstanding even after this arithmetic comparison.

This supports both retained behaviors without inventing provider APIs or taxable location. If actual provider semantics cannot be represented by this narrow net/tax/gross scope, return unsupported/inconsistent; do not approximate or extend the schema silently. A later trustworthy adapter must select its own exact verified amount representation and independently confirm all external context.
