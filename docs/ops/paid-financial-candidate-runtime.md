# Paid financial candidate runtime boundary

The internal `ProductionFinancialInspection` module validates the consistency of a caller-supplied financial envelope against validation identity extracted from an actual retained V1 or Tax V2 paid source. It authenticates neither the supplied provider input nor a current financial balance. It has no route, UI, transport binding, command, job, schema or durable observation writer.

`config/production-financial-inspection.php` ships with literal `enabled=false`. Admission requires exact purpose/version/SDK/API literals, standard loaded core configuration, a literal local/testing environment and 64-bit PHP. Production and staging refuse admission. Enabling this internal development purpose cannot enable merchant operations or a provider call. The existing Stripe SDK21.3.2/API2026-08-26.dahlia pins stay unchanged.

Factories accept only the actual typed `ProductionPaidOrderSourceV1` or `ProductionTaxPaidOrderSourceV2` and caller-owned `CurrentRows` in the original held source frame. They invoke existing retained source SQL/marker proofs before and after complete1–10 line extraction; the wrappers add no SQL/DML, commit, rollback, cleanup, source or receipt renewal. The original caller retains frame cleanup. V1 uses its original order total; Tax V2 uses buyer-reviewed tax-inclusive order total. The original capture method (`automatic` or `automatic_async`) must match the supplied PaymentIntent, which must also show exact completed collection. The source exports no original Charge ID; the envelope's Charge is bound to its PaymentIntent.latest_charge.

The returned expectation is validation identity only. It can be used for pure normalization after the held frame ends but cannot prove positive original commit, authorize provider dispatch or mint any entitlement. Both factories, normalization and explicit value access require current literal policy. Factories recheck captured policy after callback-capable source operations and before publication; withdrawal refuses without taking over cleanup.

`FinancialObservation::capture` returns a `FinancialCandidate` with an explicitly bounded `summary()` identifying `consistent_candidate`, `providerAuthenticated=false` and `unattested_input`. No account/payment/buyer identifiers, private provider fields or original source graph appear in that summary. Values refuse clone, serialize, unserialize and implicit JSON serialization. The expectation's internal identity tuple is not a public projection or financial authority.

Input bounds are1MiB, depth12,4096 nodes and100 items per collection. Only primitive values/native arrays are admitted before canonicalization; object/ArrayAccess/coercion inputs refuse without evaluating their methods. Refund/dispute lists require dense data and literal boolean `has_more`. Incomplete lists throw reason `incomplete`; malformed, unsupported or inconsistent envelopes throw `attention`; withdrawn/unsupported policy throws `disabled`. These redacted reasons do not assert a successful refund, absence of disputes or current provider state.

Charge.amount_refunded and refunded/disputed flags remain separate from per-status refund amounts/counts and historical dispute counts. Failed/canceled/pending attempts can sum above gross; succeeded refunds cannot. Separately retrieved aggregates may disagree with a complete list, so the summary retains a comparison boolean rather than declaring an atomic snapshot or settled balance. Charge.transfer and non-null connected-account/application/transfer hints refuse. No summary changes grants, downloads, rights, exclusivity, inventory, revenue or payouts.

Synthetic source journeys and SDK-shaped arrays provide local development proof only. Public Stripe documentation retrieval failed and no real account/provider interoperability, host, FPM, distributed/cache, performance, activation or full-suite result is claimed. Future authenticated retrieval, original source/commit closure and a durable observation ledger require separate implementation/review. Sean's reviewed refund eligibility/window, partial tax allocation, dispute access, rights and exclusive-resale rules remain prerequisites for financial/access/inventory effects.
