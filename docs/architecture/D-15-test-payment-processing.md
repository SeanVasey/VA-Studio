# D-15 — Durable receipt work before payment finalization

Status: accepted in [PR #63](https://github.com/VASEYDEV/VASEYAUDIO/pull/63), 2026-09-26, within Sean's continuous-development authorization. Candidate `4107d449`, tree `f2960409947b53bfedf07f0336210ca9b8a48bf0`, reached main `89d7ea1` after [CI 36220050595](https://github.com/VASEYDEV/VASEYAUDIO/actions/runs/36220050595) and two independent Codex reviews. [The implementation contract](../test-payment-processing.md) retains exact test counts and limits.

Keep receipt evidence immutable and put mutable processing state in separate durable work records. Claim work with a fresh UUID, bounded lease and retry policy. Recheck the token and deadline before every evidence write and failure update. A crashed or stale worker cannot finalize a successor's work. Scan durable eligible receipt work to recover missed dispatch and expired claims; exhausted crashed claims are quarantined under the scheduler's work lock without reviving an old worker token; asynchronous queue delivery is a latency aid, not the only recovery mechanism.

Retrieve the current Session and PaymentIntent outside database transactions using the configured own-account test credential. Validate the supported order/attempt/intent/session mapping, test/account context, exact integer amount and currency, frozen zero test tax and successful payment state. Retry status disagreements between the non-atomic provider GETs, while quarantining actual amount/identity mismatches. Retain allowlisted immutable observations and one uniquely bound payment confirmation; revalidate the full normalized retained evidence when reading an existing confirmation. Accept supported automatic asynchronous capture without requiring Charge accounting fields that Stripe may populate later.

The strongest outcome in this increment is `awaiting_finalization`. It is not an order-paid transition, a grant or a resource-release instruction. Unknown, pending and authorized outcomes retry; evidence conflicts and exhausted attempts quarantine; explicit replay is audited. Missing webhooks can be reconciled by retrieving known sessions without creating or capturing payments. The console pages by immutable intent ID using a scoped opaque `--after` UUID and emitted `NEXT_AFTER` cursor; failures still advance that sweep, and a later new sweep starts without a cursor. Browser return and existing owner status contracts do not become payment authorities.

Processing is disabled by default and limited to local/testing test-mode use; a staging receiver can retain receipts without processing them. Retain all evidence on disablement or rollback. Production account/tax/legal policy, live activation, refunds and cutover remain unresolved for their respective scopes.

The dependent [D-16 candidate](D-16-test-payment-finalization.md) extends retained order verification and agrees the WP-04/WP-08 grant/render interface before atomic inventory/promotion/order effects, unique grants, pending entitlements/outbox or `paid_exception`. Its acceptance is separate from this merged processing increment; contracts and secured delivery follow. See [the implementation contract](../test-payment-processing.md) for states, commands, fencing, evidence and acceptance limits.
