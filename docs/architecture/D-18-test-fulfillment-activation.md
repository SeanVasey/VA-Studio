# D-18 — Immutable whole-order test fulfillment activation

Status: **Approved implementation direction; dependent candidate, 2026-09-26.** This formalizes the [activation proposal](../test-fulfillment-activation-proposal.md) at `6a1d317` against implementation through `b76a3c1`. It follows D-16 paid finalization and D-17 private original issuance. D-17 prerequisite acceptance, this increment's full MySQL/SQLite CI and final independent review remain integration gates. This decision does not claim a merged activation increment, active downloads or production readiness.

Record one immutable technical activation proof per complete paid test order. Require every original contract and exact purchased asset before recording anything; no partial line can activate. Preserve the original order/finalization hashes, grants, original documents, `pending_entitlements` and `fulfillment_outbox` unchanged. The existing pending-only finalization verifier remains authoritative. An additive proof does not change a license's permissions or create customer access.

A separate disabled-by-default local/testing policy selects the configured own Stripe test account, complete-order scope, private local storage, fresh SHA-256 verification and a 300-second maximum observation age. Older checkout, processing, finalization and issuance flags are unnecessary for activating retained evidence. Buyer identity remains an unverified guest; download access is explicitly disabled. Production identity, legal terms, tax, refund/revocation and storage decisions remain unresolved for their scopes.

Compose the complete historical order/finalization and request/work/original verifiers with exact pending-entitlement membership and historical media provenance. Capture only the frozen purchase and retained source revisions. Deduplicate physical asset checks while preserving every grant's entitlement membership. Retain technical media metadata through a versioned typed digest, including exact finite binary64 measurements, to avoid duplicating large stems manifests and waveforms or weakening their identity. Keep the established 2 MiB canonical / 4 MiB encrypted evidence limits.

Verify original PDF bytes through `ContractFiles::verify` and purchased media through the strict uncached `DeliveryAssetFiles` adapter, outside every open database transaction. The media adapter streams exact bytes from sealed private revision paths, checks descriptor/path/directory identity before and after hashing, rejects public or served-root overlap and public-link chains, symlinks, hardlinks, unsafe modes and mismatched size/hash, and never creates, repairs or substitutes files. Existing synthetic scan provenance remains restricted to `testing`.

After verification, lock order → sorted grants → request/work → sorted asset revisions. Reconstruct and compare the entire graph using database evidence only, recheck policy/account and the observation window including lock waits, then insert one encrypted activation and one bounded audit atomically. Unique order/finalization keys and immutable ORM/SQL guards preserve the winner. A failed check or transaction leaves no partial proof. No lease table or queue is added: the bounded synchronous scanner can retry after interruption.

`verified_from ≤ verified_through ≤ activated_at ≤ verified_from + 300 seconds`, using UTC whole seconds. Observation cannot predate paid finalization or any required original. Exact equality at 300 seconds is allowed; older or backwards-clock checks require a fresh attempt. This bounded observation is not a continuing storage guarantee, backup/restore acceptance or atomic filesystem/database transaction.

Historical reads reconstruct and verify the original proof without current flags or file I/O. A repeated enabled activation returns the retained `activated` decision without rehashing or replacing it. Later file loss does not erase that historical decision; restore the exact original/revision and require fresh physical authorization at the later delivery boundary. Populated schema rollback refuses before removing any table or guard.

The current increment has an internal reader and console command, with no activation endpoint, automatic dispatch or customer wire-state extension. Existing owner order/checkout projections remain `contractStatus: issued` / `fulfillmentStatus: pending_activation` after issuance. The proposal's possible `activated` projection was not added by this candidate. No customer download link or permission follows from the command's result.

D-19 remains the separate access increment: an explicit bounded test-access policy, owner-session authorization, current file checks, exact revision binding, short-lived opaque authorization, atomic issuance/redemption limits and effective restrictions. Licensed exploitation limits such as `copies_downloads` are not website download caps. Guest/account recovery, refund/dispute decisions and underlying-rights changes remain distinct.

See [the implementation and recovery contract](../test-fulfillment-activation.md) for exact configuration, outcomes, storage bounds and executed-versus-pending evidence.
