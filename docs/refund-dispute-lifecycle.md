# Refund and dispute lifecycle (default-off)

Lane A5 (T19/T21, parity rows FP-040 and FP-068) built a refund and dispute state machine, a durable observation ledger, policy-governed access effects and a read-mostly staff customer/order view for the Stripe-test commerce chain. BL-42 extends the same ledger, state machine and effects to the **production tax chain** (see [Production tax chain](#production-tax-chain-bl-42)); it does not fork them. **Both are default-off, admit only Stripe test mode, and every write refuses until its policy values are set (the test chain: four configured values; the production tax chain: the DD-16 values in the order's retained machine policy).** Nothing here sends a refund, accepts a dispute, revokes a license or changes catalog availability: Sean issues refunds in Stripe and the application observes them.

## Boundary

- **Provider facts.** Only the existing authenticated GET path: `VerifyTestPayment::inspect` (own account, Checkout Session and PaymentIntent binding), then `StripeFinancialInspectionGateway::financialState` (PaymentIntent, Charge, complete refund and dispute lists filtered by PaymentIntent, repeated Charge), validated by `PaymentFinancialEvidence::capture`. The pinned SDK (21.3.2, API `2026-08-26.dahlia`) is unchanged. Provider I/O never runs inside an application transaction. Webhooks, redirects and clients are never a source.
- **Scope.** Granted (`paid`) test finalizations for the configured own account. Paid exceptions keep their existing refund-resolution workflow ([test-refunded-exception-resolution.md](test-refunded-exception-resolution.md)). The production tax chain is wired by BL-42 (below); the non-tax production chain (`ProductionPaidOrderSourceV1`) is not, and DD-14 makes the tax chain the one v1 sells through.
- **Originals.** Orders, lines, verified payments, finalizations, grants, exclusive sales, contracts, reservations and promotion uses are never written. Refunds and disputes are new evidence.

## Policy

`config/refund-dispute.php` reads `VASEY_TEST_REFUND_DISPUTE_ENABLED` (must be the boolean `true`) and four values with **no defaults**. The supported values are exactly `MachinePolicyV1`'s `refunds_and_disputes` choices; an unset, empty, unknown or extra value refuses every write before any row is locked or any provider call is made.

| Key | Supported values | Mechanism |
| --- | --- | --- |
| `refund_authority` | `authoritative_provider_operator_review` | Refunds count only from an accepted provider observation. A fully refunded line produces a review effect; downloads change only when staff suspend that line. |
| `partial_refunds` | `exact_line_allocation` | A full refund (succeeded refunds equal the paid amount) and a single-line order each have one exact allocation and are allocated automatically. Any other partial refund needs a staff allocation by line position that sums exactly to the refund and never exceeds a line's remaining total (tax included, from the verified original order payload). |
| `dispute_access` | `temporarily_block_while_reconciling` | An open dispute places one order-wide hold automatically. Won or closed releases it automatically; lost keeps it and records a review effect. Staff cannot release it while the dispute is open. |
| | `operator_review` | An open dispute records a review effect only. Staff may place an order-wide hold while a dispute is open or lost, and release it. |
| `exclusive_reopening` | `remain_sold` | A refunded or lost exclusive line records that the sale is retained. Reopening decisions refuse. |
| | `qualified_operator_review` | Staff may record a reopening decision only when the exclusive line is fully refunded or the dispute lost, no dispute is open, and the grant's downloads are held. The decision lists every other grant on the same rights scope as retained. The exclusive sale stays recorded and catalog availability is not changed; that is owner decision U-08. |

The proposed refund terms in `docs/legal/TERMS.md` section 10 are not approved and are not encoded. No supported value authorizes license revocation or inventory restock.

## State machine

Each accepted observation is a complete snapshot, so the case state comes from the newest snapshot, not from event arrival order (`RefundDisputeState`). Against the previous accepted snapshot an object may not vanish, change amount or currency, or move backwards (refund `pending → requires_action → succeeded/failed/canceled`, `succeeded → failed`; dispute warning/needs-response/under-review → won/lost/warning_closed, terminal states stay terminal). Any violation, a refund total above the paid amount, a currency mismatch, an incomplete list or unsupported data is recorded as `attention` with a review effect and no other effect; holds are never released by an attention observation. A succeeded refund that later fails is accepted, keeps its allocation and holds, and records `refund_reversed_review_required`.

Derived states: refund `none | partial | full` (succeeded only); dispute `none | open | lost | won | closed` (open wins over lost, lost over won).

## Ledger and effects

Additive migration `2026_10_24_264100_refund_dispute_lifecycle` (forward-only; `down()` always refuses) adds seven tables with SQLite and MySQL guards:

| Table | Contents |
| --- | --- |
| `refund_dispute_work` | Per-order ledger sequence and at most one leased provider-read claim (monotonic, undeletable). |
| `refund_dispute_observations` | Append-only, one per staff request: actor, request UUID, sequence, outcome, states, amounts, policy hash and encrypted canonical evidence (provider IDs only inside the ciphertext). |
| `refund_dispute_objects`, `refund_dispute_statuses` | Deduplicated provider refunds/disputes (hashed IDs) and the first observation of each status. Replays add nothing. |
| `refund_line_allocations` | Exact allocations of succeeded refunds to original lines; automatic sources carry no actor, staff ones must. |
| `refund_dispute_effects` | Append-only effects with a unique key per order, so replays add nothing. |
| `refund_dispute_holds` | Technical download holds (order-wide or one grant); the only change permitted is one release bound to a release effect. |

Parent rows (orders, lines, grants) are immutable and undeletable on their own; the new tables check their existence and order binding in insert guards instead of foreign keys, which keeps the existing empty-table roundtrips of the order migrations working (those tests drop the empty A5 tables first with `RefundDisputeFixtures::dropEmptyTables()`).

Writers lock actor User → Order → coordination row → current reads of the case. Every staff command is idempotent by request UUID (same actor and same arguments replay; anything else conflicts), requires the current sequence, refuses while a provider read is leased, and requires the latest ledger entry to be an accepted observation. Each write records an audit event (`commerce.refund_dispute.*`) with no provider IDs, buyer data or ciphertext.

## Access enforcement

`RefundDisputeAccess::assertClear` runs inside `IssueTestDelivery` and `RedeemTestDelivery` after their Order row lock, which every hold writer also takes first. A committed hold refuses new download authorizations and the redemption of authorizations issued before it (`DeliveryException('blocked')`). `ReadTestOwnerDelivery` reports an order with an order-wide hold as unavailable; a single-grant hold is enforced at issuance and redemption only. Paid-grant, Tax, free and member delivery paths are not wired to holds.

## Staff administration

Filament **Test commerce → Test customers** (read-only list, customer detail) and **Test orders and refunds** (a read-only order evidence action plus six commands: check refunds and disputes, allocate a partial refund, suspend line downloads, place a dispute hold, release a hold, record an exclusive reopening decision). Both pages reauthorize `administer-catalog` and the panel MFA rule on every Livewire request; every command reaches the domain service, which rechecks authority, MFA (locked re-read), policy and sequence. Order evidence (`StaffCommerceDirectory::orderFor`) rechecks staff authority and account scope itself. The customer list is grouped per customer, so it sorts only by aggregates (newest order, then the anchor finalization) and disables Filament's default key sort, which MySQL `ONLY_FULL_GROUP_BY` would refuse. Outside test commerce a command dialog closes with a notice. Guest customers appear by a keyed reference, never by their owner key.

## Production tax chain (BL-42)

DD-16 and DD-17 (decision register, 2026-11-10) confirm the values, so the lifecycle now runs on finalized synthetic orders of the tax-calculating production checkout (`ProductionTaxPaidOrderSourceV2`, grants in `paid_tax_*`). It is **default-off and admitted only in `local` and `testing`** (never `staging` or `production`), on the own Stripe test account, with Stripe test mode and synthetic-rehearsal provenance. It reuses the existing `refund-dispute.enabled` switch (`VASEY_TEST_REFUND_DISPUTE_ENABLED`, which production already requires false), so there is no new environment key. It reads no `refund-dispute.policy` value.

- **Which order.** Staff address a finalized batch by its `paid_tax_order_origins.public_id` (the id the buyer sees as the origin). A paid order that has not been finalized has no batch and is `not_found` to the ledger; a refused one is resolved with the separate [Resolve refused order](#resolve-refused-order-unfinalized-production-orders-fp-068) command. The ledger partitions every row by `order_source` (`test` or `production_tax`) because the chains number orders independently; a hold, object or sequence on one chain never touches an order of the other even when the numbers are equal. Merchandise (`ActiveOrderHolds`), the sales and health reports and the staff directory read only `order_source = 'test'`.
- **Policy.** The values come from the machine policy retained in the checkout order that produced the batch (the terms the buyer accepted), after `MachinePolicyV1::validate` and a match of its hash to the candidate binding every paid line carries. The chain accepts only the DD-16 values: `refund_authority = authoritative_provider_operator_review`, `partial_refunds = exact_line_allocation`, `dispute_access = temporarily_block_while_reconciling`, `exclusive_reopening = qualified_operator_review`. A value that is unset or empty is `policy_unset`; any other value (including the `operator_review` and `remain_sold` that `MachinePolicyV1` also admits) is `policy_unknown`; both refuse before a provider read or a ledger write. They are entered per host as the production machine policy, never committed (ledger PCL-16).
- **Facts.** Line amounts are the provider-calculated totals with tax included (`tax.line_total_minor`), and they must sum exactly to the order total. The batch and every line are APP_KEY-sealed and hash-checked, bound to each other, to the batch columns and to the paid line's own consistency check. Refunds and disputes come only from the authenticated own-account GET path (`StripeFinancialInspectionGateway`, then `PaymentFinancialEvidence::capture`) bound to the retained account, PaymentIntent and gross total; an event for another account, payment or currency is `attention` and writes no object. There is no webhook, redirect or client source and no provider write.
- **Allocation, holds, effects.** Exactly as for the test chain. A line and its grant are the same retained `paid_tax_grant_origins` row, so `order_line_id` and `license_grant_id` carry that id. Staff commands (`allocate`, `suspendLine`, `releaseHold`) work on the batch's public id and a line's origin public id.
- **Delivery.** `PaidTaxDownloads` refuses a new authorization, the replay of a live one and the redemption of one issued before the hold (HTTP 409, internal reason `refund_dispute_hold`) while an order-wide or that line's hold is active. The check runs after the frame has read the batch row under lock, the row every ledger writer also locks first, and in both redeem frames. The buyer's `status` response keeps its exact shape (the page validates it), so a held line shows no flag, only the refusal; owner listings can read the hold with `RefundDisputeAccess::heldGrantIds($batchId, 'production_tax')`. A released hold restores access; an authorization is never revoked or rewritten.
- **A lost dispute** keeps the order-wide hold and records `dispute_lost_review_required`. It ends a line's access only when staff suspend the line (`refund_suspension`), after which staff may release the order-wide hold so other lines flow again. No grant, original, contract or authorization row is changed: the license record is retained, and access, not the license, ends. A won dispute releases the hold automatically.
- **A refund after delivery** records the allocation and the line review and changes nothing else: new downloads still work until staff suspend the line, and the delivered attempt stays counted.
- **Exclusive.** The production chain sells no exclusive license (`ProductionTaxPaidLineAdapterV2` requires a non-exclusive line; `ExclusiveInventoryGate` refuses exclusive inventory), so no production line is exclusive: `ProductionTaxOrders::verify` fails closed on anything else, no exclusive effect is written and `qualifyExclusiveReopening` refuses with `not_qualified`. The shared exclusive code (tested on the test chain) applies unchanged if an exclusive production consumer is ever added, and nothing relists automatically. DD-17's reservation and late-payment values live in the same machine policy but are not read by this lifecycle.
- **Finalize guard (BL-42 follow-up, P2-1).** `PaidTaxGrants::finalize` re-reads the provider before it creates any grant origin, so an order refunded or disputed before the buyer finalizes it is not granted (`ProductionTaxFinalizeGuard`). Step 1 runs outside every transaction and before the locked frame: the order's retained account, PaymentIntent and gross total come from its plain `reviewed` row, and the same authenticated own-account GET the staff observation uses (`StripeFinancialInspectionGateway`, validated by `PaymentFinancialEvidence::capture`) is bound to exactly those three facts. Step 2 runs inside the locked frame before the first write and proves that the authenticated paid lines carry that account, PaymentIntent and gross; a read that does not match the locked order cannot clear it. Refusals reuse the existing vocabulary and create nothing (the order stays paid, no grant origin, no ledger row, no audit row): HTTP 409 `refund_dispute_hold` when committed refunds (succeeded plus pending) cover the gross or a dispute is open (including warnings) or lost, and 409 `refund_dispute_attention` (the ledger's outcome name) when the read fails, is incomplete, or returns another account, payment, amount, currency, mode or an inconsistent state. A partial refund, a won or closed dispute, and failed or canceled refunds do not block; the ledger covers them after finalization. The guard is admitted exactly where the lifecycle is (flag on, `local`/`testing`, own Stripe test account); elsewhere finalization is unchanged and makes no provider call. A replay of an already finalized order reads only its retained batch and makes no provider call (holds and the ledger govern it from then on). A state that changes between the read and the commit is the same race as any later refund and is picked up by the ledger.
- **Schema.** Migration `2026_11_10_288200_refund_dispute_production_tax_chain` adds `order_source`, rebuilds the per-source unique indexes and replaces the insert guards. `PaidTaxSchema` refuses any external object that names its tables, so the guards cannot check the production parents; their existence and binding are proven by the ledger's own locked transaction before any row is written (`ProductionTaxOrders::verify`). The `test` source keeps its existence checks.
- **Staff surface.** The domain services (`RefundDisputeLedger::observe/review`, `RefundDisputeActions`) accept the production batch id. The Filament pages still list test finalizations only; a production order page for finalized batches is a follow-up. Unfinalized paid production orders have their own list with the resolve command (next section).

## Resolve refused order (unfinalized production orders, FP-068)

Owner decision (Sean, 2026-11-10): when the production tax chain's paid order is refused at finalization, because `ProductionTaxFinalizeGuard` returned `refund_dispute_hold` (committed refunds cover the gross, or the dispute is lost), staff **restore the instrumental for sale and resolve the order**. Such an order has no `paid_tax_order_origins` batch, so the ledger and its hold/release path cannot see it.

- **Command.** `ResolveRefusedProductionOrder::resolve($orderPublicId, $actor)` (the checkout order's public id, not a batch id), exposed as the "Resolve refused order" action on the Filament list "Unfinalized paid production orders" (`/admin/unfinalized-production-orders`, group "Test commerce", `ProductionTaxRefusedOrderResource`, fed by `StaffCommerceDirectory::unfinalizedProductionOrders()`). Authority is the same as `RefundDisputeActions`: `administer-catalog` plus the panel MFA rule, checked before any other read (a caller who is not staff causes no provider call) and again under lock on the staff user row (`RefundDisputeAuthority::lockStaff`). Admission is the lifecycle's own: flag on, literal `local`/`testing`, Stripe test mode, own account.
- **Provider state.** The order's retained account, PaymentIntent and gross total come from its plain `reviewed` row (`ProductionTaxFinalizeGuard::reviewedFacts`); the same authenticated own-account GETs the staff observation and the finalize guard make run through `ProductionTaxFinalizeGuard::assess`, outside every transaction. Then one transaction locks the staff user row, then the checkout order row (the row finalization also locks), re-proves that no batch exists (locking read), that the sealed order and reviewed rows open and still carry the facts the provider read was bound to, and inserts the resolution.
- **When it proceeds.** Only when the read is HOLD because the **succeeded** refunds cover the gross (`full_refund`) or the dispute is lost (`dispute_lost`; a lost dispute with a covering refund is recorded as `full_refund`). The refund must have succeeded, not merely be pending: the resolution is final, so a refund that could still fail never resolves an order.
- **When it refuses (bounded reasons, nothing written).** `finalized` (a batch exists; those use the hold/release path, and no provider call is made), `not_paid` (no reviewed payment), `not_found`, `not_refused` (CLEAR: untouched, partial refund, failed or canceled refund, won or closed dispute), `reconciling` (a dispute is open, even if the payment is also fully refunded: the hold stays until the outcome), `in_flight` (refunds pending or only the charge aggregate covers the gross), `not_observed` (the read failed, was incomplete, foreign or inconsistent: ATTENTION), `disabled`, `unavailable`, and an authorization failure for anyone but current staff with MFA.
- **Record.** One append-only row in `production_tax_refused_order_resolutions` (migration `2026_11_11_000300`, classified in `RetentionSchedule`): order public id and hash, account, PaymentIntent, gross, reason (`full_refund` | `dispute_lost`), actor, observed and resolved times, and the APP_KEY-sealed provider evidence with its SHA-256 hash, plus an audit event `commerce.refused_order.resolved`. Database guards require a paid order with matching facts and no finalized batch, one row per order, and refuse any update or delete. No foreign key names a Tax255 table (its installer refuses external references), so the order link is the public id.
- **Idempotent.** A second resolve, by anyone with staff authority, returns the existing resolution (`replayed: true`) without a provider call, even if the provider state has since changed.
- **Never.** It creates no grant, license, contract or download authorization, sends nothing to the provider, and never changes, deletes or rewrites the order, payment evidence, refund or dispute records (tests snapshot every table: only the resolution and `audit_events` change). A resolved order is closed to finalization for good: `PaidTaxGrants::finalize` refuses it (HTTP 409, internal reason `refused_order_resolved`) before and inside the locked frame, whether or not the lifecycle is still admitted and even if the provider state later reverses, so no grant or download can follow.
- **Restoring the track or offer for sale.** Nothing needs releasing: the tax chain reserves no inventory and sells no exclusive line (DD-14; C4). Its order record states `inventory = unscoped_nonexclusive`, and checkout writes only the four append-only `production_tax_checkout_*` tables (`ProductionTaxCheckout`: no exclusive reservation, offer reservation, availability lock or `sold` flag exists on this chain; `ExclusiveInventoryGate` refuses exclusive inventory). So the track and offer are available exactly as before the order, at every moment, and resolution leaves every catalog table byte-for-byte unchanged. `RefusedOrderResolutionTest::test_the_track_and_offer_are_untouched_and_purchasable_again...` pins it: the offer previews identically and the same buyer can order it again after the resolution. If a future production chain ever reserves inventory, its release must go through that chain's release service from this command, not by hand-editing state.
- **Buyer view.** The generic 409 and the unchanged 404 for non-owners are preserved; `refused_order_resolved` is an internal reason code and is not returned over HTTP. Refunding the buyer remains an action in the Stripe dashboard; this command observes and records.

- **Which orders are listed (DD-17).** A paid-exception (late-paid) order also has a plain `reviewed` row, so it is listed under "Unfinalized paid production orders" and is resolvable exactly like any other unfinalized paid order.
- **What "final" means, and recovery.** The resolution row is append-only and `PaidTaxGrants::finalize` refuses a resolved order forever; there is deliberately no superseding record. `full_refund` is final only as far as the provider keeps the refund final: Stripe documents that a succeeded refund can later fail (`RefundDisputeState` accepts `succeeded` to `failed`), and the resolver treats succeeded refunds covering the gross as settled. A `dispute_lost` resolution is final by design (a lost dispute is not reversible by this system). **Recovery if a resolved order's refund later fails:** staff refund the buyer manually in the Stripe dashboard (test mode in this environment) and annotate the order in the operator notes; the order stays closed to finalization on purpose, so the buyer is made whole by the manual refund and never by a late grant. Nothing in the application reopens a resolved order.

## Owner decisions (Sean, 2026-11-10)

Recorded in the [decision register](architecture/decision-register.md) ("FP-068 follow-up, C1 and C4").

- **C1, a dispute ends download access, not the licence.** An open dispute ends download access (the order-wide `dispute_reconciling` hold) while the license itself is kept, with the dispute noted on the record (the observation, the provider-object row, the `dispute_hold_applied` effect and its audit event). A lost dispute keeps the hold and records `dispute_lost_review_required`. Staff suspension of a line ends that line's access (`refund_suspension` hold) with the licence record retained. Verified against the code on 2026-11-10 (no change needed): nothing in `app/Domain/Commerce/RefundDispute/` writes to a grant, order, contract or authorization row (the only writes are the ledger tables), a won or closed dispute is the only automatic release, and `ProductionTaxRefundDisputeTest::test_a_lost_dispute_keeps_access_ended_for_staff_review_and_never_revokes_a_grant_or_original` pins it. One path to know: after a *lost* dispute `RefundDisputeActions::releaseHold` is not refused (it refuses only while the dispute is open), so a staff member can explicitly release the order-wide hold, which restores access to unsuspended lines. That is an audited staff command (`hold_released_by_staff`), the same step the line-suspension flow above relies on; nothing restores access automatically on a lost dispute. **Staff release (Sean, 2026-11-10, amends DD-16).** Staff can lift a dispute hold, including after a lost dispute, with the existing explicit, audited `hold_released_by_staff` command; the code is unchanged and nothing restores access automatically. A lost dispute on an unfinalized order still has no batch and so no release path (documented state).
- **C4, the exclusive acceptance items are not applicable on this chain.** No production line is exclusive (`ProductionTaxPaidLineAdapterV2` requires a non-exclusive line and `ExclusiveInventoryGate` refuses exclusive inventory), so the exclusive reopening acceptance items of FP-068 are recorded as N/A for the production tax chain for that reason. The shared exclusive code stays tested on the test chain and applies unchanged if an exclusive production consumer is ever added.

## Known limitations

- **Resolved order whose refund later fails.** See the recovery procedure under [Resolve refused order](#resolve-refused-order-unfinalized-production-orders-fp-068): the resolution is permanent; staff refund the buyer manually in the Stripe dashboard (test mode) and annotate the order.
- **Stuck after attention.** While the latest ledger entry is `attention`, every staff command refuses (`not_observed`) until a later check is accepted. If the provider keeps reporting the same drift, the case and its holds stay frozen; there is no staff override. Conversely, an open dispute that arrives together with an unrelated drift places no reconciling hold, because attention applies no effect. Both need an operator-runbook step before real use.
- **Automatic multi-refund split.** When several unallocated refunds together complete a full refund, each line's total is exact but the split of each refund across lines follows line order and is not unique. A later `succeeded → failed` reversal therefore frees whichever lines that refund happened to cover; a review effect is recorded and holds are not released automatically.
- **Coverage.** The Stripe-test order chain and the production tax chain are covered. The non-tax production chain (`Paid\*` grants), free, production-free and member delivery serve different order sources and do not check holds; any future refund/dispute coverage of those chains must add hold checks there.
- **Refund before finalization (production tax).** Closed by the finalize guard above for the one case it can see: a refund or dispute that already exists at the provider when the buyer finalizes. It is not recorded as ledger evidence (a paid, unfinalized order still has no batch, so a refused finalization leaves no row for staff to find, and each retry re-reads the provider); a refund or dispute that arrives after the read and before the commit is observed by staff on the finalized batch like any other. The durable staff-visible record of a refused finalization is the refused-order resolution below. **Ownership and oracle.** Before any provider call the guard runs an unlocked buyer pre-check with the same comparison the locked frame uses (`sameOwner` of the principal's durable binding against the order's original buyer binding); a caller who is not the original buyer makes zero provider calls and gets exactly the refusal a non-owned order always got (404, whatever the order's refund state). For the owner the pre-lock read's refusal is carried as a deferred decision and raised only inside the locked frame, after `ProductionCustomerAccess::lock`, the buyer binding and the authenticated lines, so a race on ownership cannot leak it either. **What the HTTP caller sees.** Every guard refusal is a generic 409; `refund_dispute_hold` and `refund_dispute_attention` are internal reason codes for staff and tests and are not returned over HTTP. **Where it is admitted.** The guard is admitted only where the lifecycle itself is (flag on, `local`/`testing`, own Stripe test account); if the lifecycle is ever admitted on `staging`, the guard's admission must be widened together with it, never separately. **Lost dispute before finalization.** A lost dispute on an unfinalized order cannot be finalized: there is no batch to hold, so staff resolve it with the [Resolve refused order](#resolve-refused-order-unfinalized-production-orders-fp-068) command (Sean, 2026-11-10); until they do, the order stays paid and ungranted. **Partial refund before finalization.** A partial refund that exists at finalization does not block it and grants every line (DD-16: the ledger allocates the refund to lines later). **Refund aggregate.** The guard also holds when the charge's own `amount_refunded` aggregate, or the listed refunds in flight, cover the gross, so a refund list that lags the charge fails toward hold. **Timing.** A refused attempt costs up to the provider GETs of one observation (about six) for the order's own buyer; the response time can therefore differ from a clean finalization for the owner only (documented, not changed).
- **Production tax staff surface.** There is no Filament page for finalized production batches yet (see above); unfinalized paid orders have the resolve list.
